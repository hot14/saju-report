## 0. 먼저 읽어야 할 결론 3줄

1. **계정 없음(P6)과 반복 조회(가드레일 §5)의 모순을 "결제 화면 이메일 1필드 + 영수증 매직 링크"로 해소한다.** 이메일은 결과 열람 전 벽이 아니라 저장 장치다(SajuRoot 설계 계승).
2. **재접근 경로는 3개다**: 결제 직후 세션 쿠키(즉시 오픈), 영수증 이메일의 매직 링크(이후 언제든), 랜딩 푸터의 링크 재발송(이메일 분실 시). 결제 버튼은 기구매 이메일을 결제 전에 차단해 중복결제·환불 분쟁을 원천 제거한다.
3. **영수증 하단의 환불 1클릭 링크까지 확정**해 "전액 환불, 이유는 묻지 않습니다" 보증의 이행 장치를 만든다. 리스크 #1과 미비 #2(환불 이행 부재)를 한 설계로 동시 해결한다.

## 2. 설계 원칙 5개

1. **계정 없음 유지 (P6)**. 이메일 필드는 회원가입이 아니다. 비밀번호·프로필·설정 화면을 만들지 않는다. 이메일은 영수증 수신인이자 재열람 키의 소유자 주소일 뿐이다.
2. **이메일은 벽이 아니라 저장 장치** (SajuRoot 퍼널 설계 계승 [문서: competitor-intel]). 무료 퍼널(①~④)에는 이메일을 묻지 않는다. 이메일은 결제(⑤)에서만, 영수증·재열람 목적으로만 수집한다.
3. **즉시 전달 우선**. 결제 완료 = 현재 세션에서 바로 유료 결과(⑥) 오픈. 이메일 수신 여부와 무관하게 "결제와 동시에 전달됩니다"(보증 3줄)를 문자 그대로 이행한다. 이메일은 최초 열람이 아니라 재접근을 보증한다.
4. **결정론 재진입 (P1)**. 재접근은 재계산이 아니라 재열람이다. 결제 시점에 렌더된 리딩 산출물을 재생시킨다. 같은 구매는 영원히 같은 내용을 보여준다.
5. **최소 수집**. 수집하는 개인정보는 이메일 주소 1개. 생년월일·출생시각은 계산 후 세션에서 폐기하고 주문에는 **리딩 산출물만** 부착한다(입력 화면 프라이버시 라인 "입력값은 판정에만 쓰입니다"의 유료 확장). 이메일은 마케팅에 재사용하지 않는다.

## 3. 여정 설계 (단계별)

### 3.1 결제 화면(⑤): 이메일 필드

| 설계 항목 | 결정 | 사유 |
|---|---|---|
| 위치 | 상품 요약 카드와 지불 수단 사이 | 영수증은 구매의 속성이며, 지불 수단 선택 전에 보여야 월렛 사용자도 놓치지 않는다 |
| 형태 | 한 줄 필드 1개(type=email). 더블 입력·확인 절차 없음 | 마찰 최소화. 오타는 발송 고지·수정 창구(§3.2)로 흡수 |
| 검증 | 형식 검증 후 블러 시점 서버 조회(기구매 여부) | 중복결제 차단은 결제 버튼을 누르기 전에 |
| 기구매 시 | 결제 CTA가 "결제하기"에서 "링크 다시 받기"로 전환 + 안내문 1줄 | 아래 §3.4 |
| 월렛 경로 | Apple Pay·Google Pay 사용자도 이 필드는 그대로 | 월렛 결제는 이메일을 신뢰성 있게 반환하지 않는다(Apple 개인 릴레이 주소 포함). 명시 필드가 사용자에게 수신 주소 인지도도 준다 |

무료 퍼널(①~④)은 어떤 지점에서도 이메일을 요구하지 않는다. 원칙 2의 직접 적용이다.

### 3.2 결제 완료 → 유료 결과(⑥) 진입 직후

1. 리딩 즉시 오픈(원칙 3). 이메일 확인·수신 인증 등 어떤 대기도 없다.
2. 화면 상단 인라인 고지 1줄: "영수증과 재열람 링크를 보냈습니다." + 서브 1줄. 결과 열람을 방해하지 않는 라이트 토스트 또는 헤더 하단 라인(MOTION 4: 결정론적 등장만).
3. 세션 내 이메일 수정 창구: 고지 라인에 "이메일이 다르다면 지금 바꿀 수 있습니다" 계열의 수정 링크. 세션 유지 중 1회 허용, 수정 시 새 주소로 영수증 재발송, 구 주소로 변경 고지 1통 발송.
4. 세션 쿠키 발급: httpOnly · SameSite=Lax · 90일(설계값). 세션 유효 중 재방문은 이메일 경로 없이 리딩 직행.

### 3.3 영수증 이메일

| 항목 | 설계 |
|---|---|
| 발신 | `{{BRAND}} <receipt@{{DOMAIN}}>`. SPF·DKIM·DMARC 설정 필수(수신율·위조 방지) |
| 형식 | HTML + 플레인텍스트 대체본. 링크는 텍스트 버전에도 URL 노출 |
| 제목 | `{{BRAND}} · 영수증과 재열람 링크` |
| 본문 구성(상→하) | ① "결제가 완료되었습니다." ② 상품명 "전체 리딩 · 7개 주제" · 금액 {{PRICE}} · 결제 일시(Intl 로케일 서식) ③ 안내문 "아래 링크로 언제든 다시 읽을 수 있습니다." ④ 메인 버튼 "리딩 다시 열기"(매직 링크) ⑤ 보증 3줄(카피 덱 §6과 동일 문안 반복) ⑥ 환불 링크 "전액 환불 받기" ⑦ 푸터 면책(카피 덱 §1 공통) |
| 생년월일·리딩 본문 | 이메일 본문에 0노출. 이메일은 전달·스크린샷되는 매체다. 링크만 넣는다 |
| 발송 시점 | 결제 확정 webhook 수신 후 1분 내(설계 상한). 지연 시 재발송 큐 |
| 로케일 | 결제 시점 `html[lang]` 로케일로 발송. 카피는 카피 덱 `receipt.*` 키(i18n 폴백 `{locale} → en-US → ko-KR`, §7 키 제안 참조) |

**PSP 자체 영수증과의 관계**: PSP가 자체 영수증 메일을 발송하는 경우 이중 수신 혼란이 생긴다. PSP 발송 설정을 끄고 자체 영수증으로 단일화하는 것을 기본으로 한다(PSP 정책상 강제 발송이면 자체 메일이 우선 안내하도록 문구 조정. PSP 확정 시 재검, §9-6).

### 3.4 재접근 경로 3개

| 경로 | 동선 | 언제 쓰이나 |
|---|---|---|
| A. 세션 쿠키 | 재방문 시 세션이 유효하면 리딩 직행 | 같은 브라우저, 90일 내 |
| B. 영수증 매직 링크 | 이메일의 "리딩 다시 열기" → 세션 갱신 → 리딩 | 세션 종료·기기 변경·링크 보관(즐겨찾기 포함) |
| C. 재발송 페이지 `/resend` | 랜딩 푸터 "구매한 리딩 다시 보기" → 이메일 입력 → "링크 다시 받기" → 매직 링크 발송 | 영수증 삭제·스팸함 유실·링크 폐기 후 |

- 재발송 페이지는 신규 퍼널 화면이 아니다. 랜딩 하단 시트·모달로 띄우고 URL만 `/resend`로 독립시킨다(P6 화면 수 원칙 보존).
- 무료 결과의 재접근은 별도 장치 없이 재입력으로 한다. 결정론(P1)이 곧 무료 재접근 수단이다(같은 입력 = 같은 무료 결과). 이메일은 유료 구매에만 묶는다(원칙 5).

### 3.5 매직 링크 상세

| 항목 | 설계 | 사유 |
|---|---|---|
| URL | `https://{{DOMAIN}}/r/<토큰>` · 단일 불투명 경로 세그먼트 | 쿼리 파라미터는 유출 면이 많다(리퍼러·로그). 생년월일 등 입력값의 URL 인자화는 전면 금지(SajuRoot 규칙 승계 [문서: competitor-intel]) |
| 토큰 | 192비트 무작위 · base64url 32자 · 저장은 SHA-256 해시 | 추측 불가성과 저장 유출 대비 |
| 수명 | 원칙 영구(구매가 유효한 동안). 만료 시각 없음 | "언제든 다시" 약속과 일치. 폐기는 회전·환불로만 |
| 회전 | 재발송 시 신규 토큰 발급, 기존 토큰 즉시 폐기 | 유출 대응. 폐기 링크 클릭 시 "링크가 만료되었습니다" + 인라인 재발송 폼 |
| 진입 동작 | 구매 1건 → 리딩 직행 / 2건 이상 → "내 리딩" 목록(궁합·아티스트 상품 확장 대비) | 다중 구매 지원 |
| 세션 발급 | 링크 진입 성공 시 세션 쿠키 갱신(90일) | 재방문마다 이메일을 요구하지 않는다 |
| 소유자 표시 | 리딩 상단에 소유 이메일 마스킹 표시(예: `a***@gmail.com`) | 링크가 전달됐을 때의 인지적 경고 + 본인 확인 심리 |
| 링크 유출 트레이드오프 | 알려진 한계: 매직 링크 소지자는 리딩을 볼 수 있다. 완화: 고엔트로피 토큰 + 회전 + 소유자 표시. 생체·2FA 도입은 계정 체계와 함께 오버스펙이다 | 단건 $8 상품의 위험 균형 [추론] |

### 3.6 환불 1클릭 (미비 #2 동시 해결)

1. 영수증 하단 "전액 환불 받기" → `/refund/<주문 토큰>`(환불 전용 스코프, 매직 링크 토큰과 분리).
2. 환불 페이지: 안내문 1줄 + 버튼 1개. **사유 필드 없음**(선택 피드백도 비강제). "이유는 묻지 않습니다"를 UI 구조로 이행한다.
3. 실행: PSP 환불 API 호출 → 확인 이메일 → 해당 주문 매직 링크 전부 폐기 → 재진입 시 "환불된 리딩입니다" 안내.
4. 마케팅 수단으로 환불 유예(할인 제안·Retain 창) 금지. 신뢰 원칙(P7)이 전환 최적화보다 위다.

## 6. 보안·프라이버시

1. **수집 최소화**: 이메일 1필드. 생년월일·시각·도시는 세션에서 계산 후 폐기, 주문에는 리딩 산출물(렌더된 텍스트·카드 참조)만 부착. 원시 입력의 영구 저장 없음.
2. **저장**: 이메일은 저장 시 암호화(암호화 키 분리). 토큰은 해시 저장. 조회 인덱스는 이메일 해시.
3. **열거 방어**: /resend 응답 문장의 균일 정책, 레이트리밋, CAPTCHA 임계치.
4. **마케팅 미결합**: 결제 화면에 뉴스레터 체크박스·사전 동의 묶음 금지. 영수증은 거래 목적 메일이다. 수신 거부 링크도 없다(마케팅 메일이 없으므로).
5. **법률**: 이메일·주문 기록 보존 기간은 로케일별 법령 확인 항목으로 남긴다(구현 전 법률 검토. 전자상거래·세무 증빙 요건은 PSP·사업자 등록 지역에 따라 상이).
6. **PSP 고위험 업종(R7·Q18) 완화**: 영수증·환불 이행 기록은 chargeback 분쟁의 1차 방어 증빙이 된다. 결제 화면 면책 문구와 함께 심사 증빙 세트로 제출 가능 [추론: PSP 심사 관행].

## 7. 기술 요구사항 (구현 스케치)

- **데이터 모델(개념)**: `purchases(order_id, email_hash, email_enc, product, locale, price_cents, created_at, refunded_at)` · `readings(order_id, artifact_ref)` · `access_tokens(token_hash, order_id, created_at, rotated_at, revoked_at)` · `refund_tokens(token_hash, order_id)`.
- **결제 확정 트리거**: PSP webhook 수신 → 리딩 산출물 확정(세션 폐기 전 보관) → 영수증 발송 큐. webhook 지연 시 결제 완료 화면의 발송 고지는 "보내고 있습니다" 상태로 전환하지 않는다(고지 문안은 발송 확정 후 1회만. 원칙 3의 즉시 오픈과 분리).
- **이메일 인프라**: 발송 서비스 선택은 구현 계층 사항. 도메인 인증 3종 세팅을 완료 조건으로 한다.
- **i18n 키 제안**(i18n-spec §3 구조 준수): `payment.email.{label,helper,error}` · `payment.existing.{notice,cta}` · `result.receipt.{toast,sub,edit}` · `resend.{title,label,cta,done,done-sub}` · `email.receipt.{subject,headline,product,guide,cta,refund,disclaimer}` · `refund.{title,body,cta,done}` · `link.expired` · `link.refunded`.
- **카드·OG와의 접점**: 공유 카드의 루프백 URL은 랜딩(신규 유입용)이고 매직 링크와는 별개 체계다. 리딩 페이지의 공유는 카드만 노출하는 공유 링크로만 허용한다. 상세는 `docs/share-card-v2-spec.md` §12.

## 10. 설계 한계 선언

- PSP 미정(Q18)이므로 webhook·환불 API·이상 결제 처리의 구현 세부는 확정 계층 선택 후 재검이 필요하다.
- 이메일 발송 인프라·도메인 인증의 운영 검증(수신율)은 구현 단계 과제다.
- 보존 기간·국제 이전 등 법률 검토는 본 문서 범위 밖이다(§6-5).
- 세션 90일·레이트리밋 수치는 설계 기본값이며 실측 후 조정 가능하다. 원칙(§2)은 불변.
