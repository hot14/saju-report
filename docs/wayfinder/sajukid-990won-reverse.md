1. 사주아이는 모든 유료 상품을 990원 단건으로 통일하고, 결제는 "츄르" 화폐 사전 구매(990원/개 고정 단가, 4티어 패키지)를 거쳐 소비하게 만든다. 실측 결제수단은 토스와 카카오페이뿐이고, 구매 1회당 냥(채팅 화폐) 보너스를 줘서 유료 결제가 무료 수다방 습관으로 이어지게 설계했다.

3. 데이터 계층이 클라이언트에 열려 있다. Firestore 보안 규칙이 문서 읽기와 컬렉션 LIST를 사용자 경로에 전부 허용하고, 상위 컬렉션만 차단한다. 본인 세션 토큰으로 자기 데이터 전체를 한 번에 덤프할 수 있었고, 이것 자체가 SAJU 설계에 반영해야 할 보안 교훈이다.

## 4. 콘텐츠 스키마 (AI 해설의 구조화)

- 사주해설 `sajuResult` 13섹션: 오행으로_보는_사주·한마디로_표현하면·따뜻한_위로와_칭찬·성격·일주와_십성·친구·힘을_주는_문구·신랄한_비판·돈·지역·직업·이성·가족. 각 섹션 {title, description}. (`data/firestore/members/c2084f25*/sajuReadings.json`)
- 궁합 `result`: 궁합점수·연애궁합·결혼궁합·자식궁합·가족간궁합·오행의_조화·잘_맞는_부분·잘_맞지_않는_부분·서로에_대한_솔직한_생각·서로가_바라보는_나·서로에게_바라는_점·관계에_도움을_주는_문구·한마디로_표현하면 + score 필드. 양쪽 팔자·만세력 총량(sipsung/오행/신살/형충회합)을 문서에 통째로 저장해 재계산 없이 재열람 가능. (`data/firestore/goonghaps.json`)
- 대운 `daewunReport`: report + periodReports + periodStatuses(파트별 생성 상태 머신) + fortuneData + tokenUsage. 10년 구간을 파트로 쪼개 순차 생성하고, 실패 지점부터 이어 생성한다. (`data/firestore/members/*/daewunReport.json`)
- 파이프라인 메타: 모든 생성물에 {runId, status, lastRunAt, errorMessage}를 붙여 생성 작업을 추적한다.

SAJU 시사점: 남촌 물상 해설도 섹션 스키마(예: 물상·변화원리·한줄요약·위로·행동제안)로 고정하면 UI 재사용·부분 재생성·품질 검수가 전부 구조화된다. honbit 역분석의 AEO 결론과 겹치게, 스키마 필드명 자체가 한국어 키로 박혀 있어 그대로 노출해도 검색엔진·AI 답변 친화적이다.

## 5. 전환 퍼널 설계

1. 진입: 홈에서 "오늘의 운세 뽑기"(무료, 로그인 유도 문구 "로그인하면 기기가 켜진다냥") → 가볍게 통과
2. 습관: 수다방 무료 수다권 매일 자동 지급(밤 11시) → 일일 재방문 고리
3. 첫 결제: 해설 열람 시점에만 990원(츄르 1개) 요구 → 저항 최소화. 리뷰 섹션에 "990원이래서 재미로 봤는데"류 후기를 배치해 가격 정당화
4. 재결제: 결제 1회마다 냥 보너스 → 무료 채팅 횟수 증가 → 다음날 재방문 → 남은 츄르 소진 욕구
5. 확장: 프로필 추가(가족·친구)가 곧 소비처 확대. 실측에서도 1월에 프로필 8개를 만들며 궁합 15회를 소비했다

## 6. 보안 관찰 (SAJU 설계 교훈)

- 클라이언트가 Firestore를 직접 읽는다(REST + Listen 채널). 보안 규칙은 `users/{uid}/**` 읽기를 허용하고 listCollectionIds와 상위 컬렉션만 차단한다. 결과적으로 로그인 세션만 있으면 자기 데이터 전체를 페이지 UX 우체로 한 번에 덤프할 수 있다(본 아카이브가 그 방법).
- 세션 토큰이 localStorage의 `firebase:authUser:*` 키에 평문 저장된다. XSS 시 토큰 탈취 = 데이터 전체 유출.
- SAJU는 (1) 개인 데이터 조회를 서버 경유 API로만, (2) 대량 LIST 대신 페이지네이션+필요 필드 한정, (3) 토큰은 httpOnly 쿠키로 관리하는 쪽을 채택한다. service/security P707B 설계와 일치하며, 이번 실측이 그 근거가 된다.
