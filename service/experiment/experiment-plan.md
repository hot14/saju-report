# SajuRoot 첫 유입 실험 설계 (wayfinder #14)

- 작성: 2026-10-02
- 대상 산출물: `service/experiment/` (정적 사이트, GitHub Pages 배포 구조)
- 목적: 고객 0 · 유입 0 상태에서 최소 유입 실험으로 수요 신호를 측정 가능하게 만든다.
- 성공 판정의 축은 "이메일 제출"이다. 차트 완주는 보조 신호다.

## 1. 실험 구조

랜딩 1장(`index.html`)과 무료 차트(`chart.html`) 두 화면으로 실험한다.

- 랜딩: 헤드라인, 계산 과정 소개, 무료 차트 CTA("무료로 내 패턴 보기"), 이메일 수집 폼.
- 차트: 생년월일과 출생시각(선택, 모름 체크)으로 여덟 글자를 계산하고, 절기와 진태양시 계산 근거까지 결과 카드로 보여준다. 결과 하단에서 이메일을 다시 수집한다.
- 두 화면의 폼은 모두 숨은 필드 `src`(유입 경로)와 `page`(landing 또는 chart)를 함께 전송한다.

## 2. 유입 채널 3개 (honbit 아카이브 역분석 기반)

근거 문서: `docs/wayfinder/honbit-channel-reverse.md`. honbit(11,655페이지 사이트)의 유입 구조를 셀럽 의존 요소를 제거하고 개념 의존으로 치환한 3개 채널이다.

| 채널 | src 코드 | 진입 콘텐츠 (1줄 예시) | 예상 반응률 근거 |
|---|---|---|---|
| ① 개념 롱테일 SEO/AEO | `seo` | "일간 열 가지(갑목부터 계수까지) 개념 페이지 각각에 '내 일간 무료 계산' 링크를 심어 검색·AI 답변 유입을 모은다" | honbit은 idol 842 + blog 398 = ko 페이지의 95.8%가 인덱서블 콘텐츠로 검색 유입을 모았다(출처: `data/pages.json` 집계). 셀럽 이름을 물상 개념으로 바꾸면 같은 구조가 되고, "{개념} 사주" 검색은 셀럽 검색보다 의도 일치율이 높다. 채널 배분 판정에 필요한 최소 조건: 각 채널은 서로 다른 `src` 코드로만 구분되며, 링크는 `https://(배포 주소)/?src=seo` · `?src=community` · `?src=social` 형태다. `src` 없는 방문은 `direct`로 기록된다. 같은 브라우저에서 다른 채널 링크로 다시 들어오면 마지막 접점으로 갱신한다(마지막 접점 귀속, localStorage `sajuroot_src`).

## 3. 사전 기준 (N명 중 M명)

판정은 "기간 T일 동안 채널별 N명 도달 중 M명 이메일 제출" 구조로 한다.

- 수치(N, M, T)는 오너 확정 필요. 이 문서에서 수치를 확정하지 않는다.
- 예시 구조(오너가 채워 넣을 자리): `T = ( )일, seo N=( ) 중 M=( ), community N=( ) 중 M=( ), social N=( ) 중 M=( )`.
- 판정 규칙: 기간 종료 시 기준 미달 채널은 다음 실험 전에 설계를 변경한다. 변경 후보는 진입 콘텐츠 교체, 랜딩 헤드라인 교체, 채널 폐지이다. 기준 달성 채널은 다음 실험에서 물량을 늘린다.
- 보조 신호(참고용, 판정 아님): 차트 완주율, 랜딩에서 차트로 넘어가는 클릭 여부(간접 추정), 결과 하단 이메일 제출 비중(`page=chart`).

## 4. 측정 방법

GitHub Pages는 서버 로그가 없다. 측정은 폼 제출 payload와 수동 집계 두 가지로 한다.

### 4-1. 폼 제출 수 (자동 집계 가능)

- 이메일 폼은 Formspree 같은 무료 폼 엔드포인트로 POST한다(`{{FORM_ENDPOINT}}` 토큰에 주소를 넣는다).
- 폼 제출 1건마다 `src`, `page` 필드가 함께 전송된다. 폼 서비스 대시보드에서 제출 목록을 내려받아 `src` 값별로 세면 채널별 이메일 제출 수가 된다.
- `{{FORM_ENDPOINT}}`가 비어 있으면 폼은 mailto 폴백으로 동작한다. 이 상태의 메일은 자동 집계가 안 되므로, 측정을 시작하려면 먼저 폼 엔드포인트를 연결해야 한다.

### 4-2. 차트 완주 수 (수동 집계 기준)

무료 정적 호스팅으로는 차트 완주를 서버가 기록할 수 없다. 그래서 1차 실험에서는 아래 기준으로 수동 집계한다.

- 차트 완주의 정의: 폼 제출이 유효해 결과 카드(일간 배지 · 여덟 글자 표 · 계산 근거)가 화면에 렌더된 상태.
- 집계 불가 문제의 1차 처리: 차트 완주자만 볼 수 있는 결과 하단 이메일 폼의 제출 수(`page=chart`)를 완주의 하한(프록시)으로 삼는다. 즉 실제 완주 수는 "page=chart 제출 수" 이상이다.
- 보완 수동 집계: 각 채널 게시물의 플랫폼 제공 지표(조회, 클릭, 링크 탭 수)를 기간 종료 시 기록하고, 폼 제출 수와 나란히 대조한다. 이 대조표가 채널별 N명(도달)의 근거가 된다.
- 정밀 집계가 필요해지는 시점(다음 실험 설계 변경 후보): 무료 방문자 카운터(예: GoatCounter 무료 플랜)를 두 화면에 붙여 차트 완주 이벤트를 직접 세는 방식. 외부 유료 서비스 금지 규칙 안에서 무료 플랜만 검토한다.
- 알려진 한계: 같은 사람이 여러 번 제출하면 중복 집계된다. localStorage로 이메일 제출을 1회만 유도하지만(macOS 사파리 등에서 저장이 차단되면 예외), 브라우저를 바꾸면 중복이 가능하다. 1차 실험에서는 이 한계를 문서로 남기고 정밀화를 다음 실험 과제로 미룬다.

## 5. 배포 절차

1. 오너 승인 (필수 단계): 이 폴더의 배포 가능 상태(빌드 · 검증 결과 포함)를 확인하고 배포를 승인한다. 승인 전에는 push하지 않는다.
2. 승인 후: `service/experiment/`를 `design-ssot` 브랜치에 커밋 · 푸시한다. 이번 작업 산출물은 커밋하지 않은 상태다(오너 승인 대기).
3. GitHub Pages가 `design-ssot` 브랜치에서 배포한다. Pages 빌드 대기(최장 수 시간)가 있으므로 배포 확인은 라이브 URL 최종 확인으로 한다.
4. 배포 후 채널 링크 3종(`?src=seo` · `?src=community` · `?src=social`)이 실제로 열리고, 폼 제출이 폼 서비스 대시보드에 기록되는지 확인한다. 확인 항목: `src` 값이 payload에 보이는지.
5. 측정 기간 종료 후 §3 판정 규칙을 적용한다.

## 6. 브랜드 법 준수 (이 실험 세트에 적용된 것)

- fortune-telling/destiny/점성술/타로 어휘 0. 운세 계열 단어는 policy.json 고지문 인용("운세가 아니라 자기 이해 도구") 1건뿐이며, 이는 prototype(wayfinder #13)부터 적용된 고지문 예외다.
- em-dash(U+2014)와 en-dash(U+2013) 0건. 다크 배경 0(배경은 순백 #FFFFFF 단일). 오컬트 심벌 0(이모지 · 신비 도형 없음, 바코드는 Swiss Ledger 카드 문법의 장식 선이다).
- 브랜드명 SajuRoot 실명 사용. 가격은 `{{PRICE}}` 토큰 유지.
- 남촌 원문 인용 없음. 물상 설명은 `service/content/stems.json` 재구성 콘텐츠만 사용하고, 비검증 근거가 섞인 물상에는 policy.json의 unverifiedGuard에 따라 비검증 표기를 붙였다.
- 계산은 전부 `service/engine`의 결정론 엔진(computeChart)이 한다. 같은 입력은 항상 같은 결과를 만든다는 문장을 화면에 고정 노출한다.
